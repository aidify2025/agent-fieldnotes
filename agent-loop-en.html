02 · Inside a complete agent loop

Understand the loop through messages, tool call IDs and stop reasons.

Principle

A model response may contain text, one tool request or several. The host must first save the model response, execute authorized tools, pair each result with its original call ID, append the results to message history and request the model again. The model then decides based on new observations. A loop therefore accumulates verifiable observations rather than repeating the same prompt.

Implementation steps

  1. Prepare system rules, the current user objective, message history and permitted tool definitions.
  2. Call the model and save its complete assistant response before reading the structured list of tool calls.
  3. Validate each tool name, its arguments and its permissions. Execute it and return a success or error result with the same call ID.
  4. If there are no tool calls, run business acceptance checks. If a turn, time or cost limit is reached, record a constrained termination rather than success.

Worked example

For “Find the contract expiration date,” the model emits call_1: search({query:"expiration date"}). The host finds page 8 and returns the result for call_1; the model answers with that evidence. If the tool times out, return an identifiable timeout rather than a fabricated search result. The model may narrow its search, but the runtime still limits retries.

Code walkthrough

# Python-style pseudocode: model and execute are application adapters
for turn in range(MAX_TURNS):
    reply = model(messages, tools)
    messages.append(reply)
    if not reply.tool_calls:
        return verify_answer(reply)  # Business acceptance is separate from model stopping
    for call in reply.tool_calls:
        result = execute_with_policy(call)
        messages.append(tool_result(call.id, result))
return {"status": "budget_exhausted"}
  • Preserve the assistant message containing the calls; otherwise results arrive without their corresponding requests.
  • Errors are observations too. Distinguish timeouts, permission denials and invalid arguments instead of turning every failure into an empty result.
  • The reference project executes multiple tools sequentially with a for loop in s02. Multiple requests in one turn do not imply parallel execution.

Common pitfalls

No tool call only means the model wants to stop this turn. It does not prove tests passed or a file was saved. Do not compact away a pending call record before its result returns.

Check your understanding

  • Every tool result has exactly one valid call ID.
  • A model that continually requests tools must exit when its budget runs out.
  • Tool failures are returned as errors and never counted as successful calls.
