11 · State、节点与 Reducer

State 是协议，节点返回增量，Reducer 决定如何合并。

原理与边界

在图里，State 是各节点共享的数据契约。节点读取当前状态并返回需要更新的字段，不必返回全部对象。未配置 reducer 的字段通常被更新值覆盖；并行节点写同一字段没有合适合并规则时可能发生并发更新错误。列表追加、按 ID 替换、集合合并具有不同语义，不能只为消除报错随便选一个。

分步实现

  1. 先定义字段归属和类型：messages、evidence、decision、report_id。
  2. 为可能并发写入的集合定义 reducer，明确重复、顺序和冲突如何处理。
  3. 节点只返回增量，避免复制旧状态覆盖其他分支的新内容。
  4. 用相同输入与重复更新验证合并函数，检查是否满足所需的幂等或交换性质。

具体例子

付款审查与违约审查各返回一条证据。使用列表追加能保住两条，但重试同一分支可能重复；按 evidence_id 合并能去重，但同 ID 不同内容还需要版本规则。add_messages 按消息 ID 管理消息，不能简单理解成永远 append。不要把密钥放入 State：它可能进入 checkpoint 与日志。

代码与解释

# 独立可运行的 Python reducer
from typing import Annotated, TypedDict

def merge_evidence(old, new):
    by_id = {x["id"]: x for x in old}
    for x in new:
        by_id[x["id"]] = x
    return list(by_id.values())

class State(TypedDict):
    evidence: Annotated[list[dict], merge_evidence]
# 同 ID 最后写入覆盖；并发冲突需另外制定版本策略
  • 覆盖适合单值状态，追加适合事件列表，按 ID 合并适合可更新实体。
  • set 去重会丢失顺序，不能用于必须有序的消息时间线。
  • Reducer 不应发外部请求，否则一次状态合并就引入隐藏副作用。

常见误区

看到并发写错误就给所有字段加 operator.add，会把金额、状态或重复证据错误累加。字段的业务含义应先于框架语法。

理解自测与验收

  • 两分支结果都能保留。
  • 重复同一更新不产生额外证据（若契约要求幂等）。
  • 同 ID 冲突有可解释的处理规则。

12 · 条件边、Command 与工具循环

数据更新与下一步路由要一起设计。

原理与边界

普通边表达确定后继，条件边根据状态选择后继，Command 可以同时携带状态更新与跳转。模型工具循环就是 model→tools→model，在没有工具请求时走结束分支。路由器不应靠模型自然语言中是否出现“完成”判断，而应读取结构化状态或已经验证的工具请求。

分步实现

  1. 列出合法状态与结束状态，先画有穷的控制图。
  2. 节点返回数据更新，路由函数仅根据已验证字段决定下一步。
  3. 需要原子表达更新和跳转时使用 Command，避免同时添加导致双重调度的边。
  4. 循环设置递归限制，并在业务状态中记录独立预算和终止原因。

具体例子

审查结果若 evidence_complete=false，走检索补证据；若证据完整且 risk=high，走人工审核；其余走报告生成。模型输出未知 risk 值时应先校验，不能默认走“低风险”。图的结束仅代表没有后继任务，仍需检查报告是否通过业务验收。

代码与解释

# LangGraph Graph API 核心片段，需要已有节点与 State
from langgraph.graph import StateGraph, START, END

g = StateGraph(State)
g.add_node("review", review)
g.add_node("retrieve", retrieve)
g.add_node("report", report)
g.add_edge(START, "review")
g.add_conditional_edges("review", route, {
    "need_evidence": "retrieve", "ready": "report"})
g.add_edge("retrieve", "review")
g.add_edge("report", END)
app = g.compile()
  • route 的返回值必须属于显式路由集合。
  • 代码片段中的 State/review/retrieve/report/route 是应用定义，不能单独运行。
  • 边表达调度，不替代权限：report 节点中的写入仍需执行层校验。

常见误区

静态边与 Command.goto 同时指向不同节点，可能产生非预期分支。循环有出口但条件永远达不到，也仍会耗尽预算。

理解自测与验收

  • 对每个合法状态断言路由目标。
  • 无效状态明确失败而不是进入默认成功分支。
  • 连续补证据无进展时有限退出。

13 · Superstep、Send 与扇出汇合

并行不是画两条箭头，还要决定何时等待与怎样合并。

原理与边界

同一 superstep 中的节点读取该阶段的输入状态，各自产生更新，再在阶段边界合并。固定并行适合提前知道的分支，Send 适合运行时才知道数量的任务。并行缩短的是独立部分的墙钟时间，不自动降低总 token 成本；分支越多，失败和限流处理越重要。

分步实现

  1. 确认分支没有必须先后发生的数据依赖。
  2. 固定分支使用显式扇出和需要等待的汇合边；不同长度路径不要假定任意入边自动等齐。
  3. 动态分工为每个 Send 提供独立输入，公共结果字段设置 reducer。
  4. 汇合节点校验期望任务数、失败项与重复项，再决定部分成功或重试。

具体例子

合同有三项审查，每项独立用时 2、4、3 秒。理想并行主体耗时 4 秒，串行 9 秒；还要加上规划、汇总和排队时间。若第四项依赖付款审查结果，它不能和付款审查同时启动。某个 worker 失败时，汇总不能把“收到两个结果”当作全部完成。

代码与解释

# LangGraph 片段：相关节点和 State 由应用提供
from langgraph.types import Send

def dispatch(state):
    return [Send("worker", {"item": item})
            for item in state["items"]]

# 固定并行汇合应显式表达等待集合，例如：
g.add_edge("start_review", "payment")
g.add_edge("start_review", "liability")
g.add_edge(["payment", "liability"], "summarize")
  • 先启动所有 futures 再收集结果；在创建每个 future 后马上等待可能把并行写成串行。
  • 设置并发上限，防止大量动态任务冲垮模型与数据库配额。
  • 结果应包含任务 ID，不能用完成顺序推断原任务归属。

常见误区

并行写同一个报告文件容易覆盖；让 worker 返回独立结构，汇总节点负责最终输出通常更容易验证。

理解自测与验收

  • 慢分支结束前汇总不执行。
  • 结果乱序仍按任务 ID 正确归属。
  • 部分失败时报告明确列出缺失项。
