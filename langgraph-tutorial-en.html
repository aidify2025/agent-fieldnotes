11 · State, nodes and reducers

State is a contract; nodes return updates; reducers define how updates merge.

Principle

In a graph, State is the data contract shared by nodes. A node reads current state and returns only fields to update, not necessarily the entire object. Fields without a reducer are generally overwritten by updates; concurrent writes to the same field without a suitable merge rule may cause an update error. List append, replacement by ID and set union have different meanings. Do not choose one merely to suppress an error.

Implementation steps

  1. Define field ownership and types first: messages, evidence, decision and report_id.
  2. Define reducers for collections that may receive concurrent writes, specifying duplicate, ordering and conflict behavior.
  3. Return only updates from nodes, avoiding copies of old state that overwrite newer data from other branches.
  4. Test merge functions with identical inputs and repeated updates, checking the required idempotency or commutativity properties.

Worked example

Payment and liability reviews each return one evidence item. Appending preserves both, but retrying a branch may duplicate an item. Merging by evidence_id deduplicates, but different content with the same ID still needs a version policy. add_messages manages messages by ID; it is not simply unconditional append. Keep secrets out of State because they may enter checkpoints and logs.

Code walkthrough

# Standalone Python reducer
from typing import Annotated, TypedDict

def merge_evidence(old, new):
    by_id = {x["id"]: x for x in old}
    for x in new:
        by_id[x["id"]] = x
    return list(by_id.values())

class State(TypedDict):
    evidence: Annotated[list[dict], merge_evidence]
# Last write wins for the same ID; concurrent conflicts need a separate version policy
  • Overwrite suits single-value state, append suits event lists, and merging by ID suits updatable entities.
  • Set-based deduplication loses order and is unsuitable for message timelines that must remain ordered.
  • A reducer should not make external requests; otherwise merging state introduces hidden side effects.

Common pitfalls

Adding operator.add to every field after a concurrent-write error can incorrectly accumulate amounts, statuses or duplicate evidence. Define business semantics before framework syntax.

Check your understanding

  • Results from both branches are preserved.
  • Repeating the same update produces no extra evidence if the contract requires idempotency.
  • Conflicts involving the same ID have an explainable resolution rule.

12 · Conditional edges, Command and tool loops

Design data updates and next-step routing together.

Principle

A normal edge expresses a fixed successor, a conditional edge selects a successor from state, and Command can carry both a state update and a jump. A model tool loop is model → tools → model, with an end branch when no tools are requested. A router should inspect structured state or validated tool requests rather than search model prose for the word “done.”

Implementation steps

  1. Enumerate valid and terminal states, then draw a finite control graph.
  2. Nodes return data updates. Routing functions choose the next step using only validated fields.
  3. Use Command when an update and a jump should be expressed together. Avoid adding edges that cause duplicate scheduling.
  4. Set a recursion limit for loops and separately record a business budget and termination reason in state.

Worked example

If evidence_complete=false, retrieve more evidence. If evidence is complete and risk=high, route to human review; otherwise generate the report. Validate unknown risk values instead of defaulting to low risk. Graph termination only means there are no successor tasks; the report must still pass business acceptance.

Code walkthrough

# LangGraph Graph API fragment: requires existing node functions and State
from langgraph.graph import StateGraph, START, END

g = StateGraph(State)
g.add_node("review", review)
g.add_node("retrieve", retrieve)
g.add_node("report", report)
g.add_edge(START, "review")
g.add_conditional_edges("review", route, {
    "need_evidence": "retrieve", "ready": "report"})
g.add_edge("retrieve", "review")
g.add_edge("report", END)
app = g.compile()
  • route must return a value from the explicitly defined routing set.
  • State/review/retrieve/report/route are application-defined in this snippet, so it cannot run independently.
  • Edges define scheduling, not authorization. Writes inside the report node still require execution-layer validation.

Common pitfalls

A static edge and Command.goto targeting different nodes can create unintended branches. A loop with an exit still exhausts its budget if the exit condition is never reachable.

Check your understanding

  • Assert the routing destination for every valid state.
  • Invalid state fails explicitly instead of falling through to a successful default branch.
  • Exit within a bounded number of attempts when repeated evidence retrieval makes no progress.

13 · Supersteps, Send and fan-out/fan-in

Parallelism needs more than two arrows: decide what to wait for and how to merge.

Principle

Nodes in the same superstep read that step’s input state, produce individual updates, and merge them at the step boundary. Fixed parallelism suits branches known in advance; Send suits tasks whose count is known only at runtime. Parallelism reduces wall-clock time for independent work, not necessarily total token cost. More branches make failure handling and rate limiting more important.

Implementation steps

  1. Confirm the branches have no data dependencies requiring a specific order.
  2. For fixed branches, use explicit fan-out and join edges with a defined wait set. Do not assume any incoming edge automatically waits for all paths of different lengths.
  3. Give each Send independent inputs for dynamic delegation and assign a reducer to shared result fields.
  4. At the join, validate expected task count, failures and duplicates, then decide between partial success and retry.

Worked example

Three independent contract checks take 2, 4 and 3 seconds. Ideally their parallel work takes 4 seconds instead of 9 sequentially, plus planning, aggregation and queueing overhead. A fourth check that depends on the payment result cannot start alongside the payment check. If a worker fails, receiving two results must not be mistaken for completing all work.

Code walkthrough

# LangGraph fragment: application supplies related nodes and State
from langgraph.types import Send

def dispatch(state):
    return [Send("worker", {"item": item})
            for item in state["items"]]

# A fixed parallel join should express its wait set explicitly, for example:
g.add_edge("start_review", "payment")
g.add_edge("start_review", "liability")
g.add_edge(["payment", "liability"], "summarize")
  • Start all futures before collecting results. Waiting immediately after creating each future can accidentally serialize the work.
  • Set a concurrency limit so a large number of dynamic tasks does not overwhelm model or database quotas.
  • Include task IDs in results; do not infer task identity from completion order.

Common pitfalls

Parallel writes to one report file can overwrite each other. It is usually easier to verify independent worker outputs aggregated by one final-output node.

Check your understanding

  • Aggregation does not execute before the slow branch finishes.
  • Out-of-order results are still assigned correctly by task ID.
  • On partial failure, the report explicitly lists missing items.
