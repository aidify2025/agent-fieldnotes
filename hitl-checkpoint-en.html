14 · Checkpoints, threads and crash recovery

A checkpoint stores state, not a suspended Python call stack.

Principle

A checkpointer saves graph state at execution boundaries so the same thread can continue, inspect history or branch from old state. thread_id identifies a logical checkpoint history, not an operating-system thread. InMemorySaver is useful for demonstrations but loses data when the process exits. Surviving restarts requires a persistent backend, correct transactions and recovery tests. Replaying a checkpoint does not undo side effects in external services.

Implementation steps

  1. Assign each business session a stable, authorized thread_id.
  2. Choose a storage backend and configure migrations, encryption, access controls and backups.
  3. Identify which nodes may rerun during checkpoint recovery and isolate operations with side effects.
  4. After replay or update_state creates a branch, preserve parent-version relationships to avoid mistaking an old branch for the latest result.

Worked example

A report is written to an external system, then the process crashes before the next checkpoint. After recovery, the executor may create the report again because it does not know the write completed. This is a commit window between two systems. Use a stable idempotency key, query the write result or coordinate with a transactional outbox. Enabling a checkpointer alone does not establish exactly-once behavior.

Code walkthrough

# LangGraph in-memory demonstration: not persistent across process restarts
from langgraph.checkpoint.memory import InMemorySaver

app = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "contract-42"}}
app.invoke(initial_state, config)
snapshot = app.get_state(config)
# In production, use an appropriate persistent backend and verify authorization and recovery semantics
  • A checkpointer manages task state; Store manages cross-thread memory. Their responsibilities differ.
  • A client must not gain access to another user’s task simply by guessing its thread_id.
  • Replaying downstream work may consume model tokens or invoke tools again. Explain those effects to the operator.

Common pitfalls

Calling an in-memory checkpoint production persistence loses tasks on restart. Treating node replay as a rollback of the external world can cause duplicate payments or emails.

Check your understanding

  • Inject crashes before writes, after writes and before checkpoints.
  • After recovery, task state is consistent and external writes are not duplicated.
  • User A cannot read or resume user B’s thread.

15 · Interrupts: approve, reject or edit before resuming

Resumption restarts the node, so code before the interrupt may run again.

Principle

interrupt(payload) hands a pending decision back to the outside world and saves execution state. Resume with the same thread_id and Command(resume=value). It does not freeze a Python call stack on one line: the containing node starts again, and the interrupt receives the resume value. External writes before an interrupt are therefore dangerous. Separate approval from execution and recheck arguments immediately before executing.

Implementation steps

  1. Include the proposed action, recipient, version and digest in a serializable approval payload.
  2. The node calls interrupt; an external UI displays the actual arguments and collects approval or rejection.
  3. Resume the same thread, validate the decision and return an approved state.
  4. A subsequent execution node rechecks the digest and permissions, then uses an idempotency key for the business action.

Worked example

An approval node logs “entering review” before interrupt. That log appears again on resume, as expected. If that position sent an email instead, it would send twice. Edit-and-approve must not blindly trust frontend data either: changed arguments must pass schema validation, resource authorization and content validation again, with a new approval where necessary.

Code walkthrough

# Core LangGraph node fragment, used with a checkpointer
from langgraph.types import interrupt, Command

def approve(state):
    decision = interrupt({"report": state["report"],
                          "version": state["version"]})
    return {"approved": decision is True}

# The graph also needs a conditional edge routing on approved
app.invoke(Command(resume=True), config)  # Same thread_id as the initial call
  • Avoid side effects before an interrupt; unavoidable ones must be idempotent.
  • Do not swallow interrupt control exceptions with a broad except.
  • The order of multiple interrupts affects resume matching. Do not arbitrarily reorder them or conditionally skip them.

Common pitfalls

A rejection must not become an automatically retryable error. If approval is not bound to a version, content changes while waiting may result in an unapproved action.

Check your understanding

  • Rejection produces zero external writes.
  • On resume, node entry count increases but send count remains one.
  • A version change invalidates the earlier approval.
